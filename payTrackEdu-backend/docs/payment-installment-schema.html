Payment & Installment Database Schema

payTrackEdu backend • Generated from the JPA entity model • October 2026
The important idea: a payment-plan installment is a reusable template. An enrollment installment is a student-specific snapshot created from that template. They are stored in different tables and are not directly linked.

Why the old installment remains

Current behavior in the application
1. Create plan
Payment plan and its template installments are created.
→
2. Create enrollment
generateForEnrollment() copies the registration fee and plan templates into student installments.
→
3. Delete template
The template has is_deleted = true. The copied student installment does not change.
→
4. Update enrollment
Only enrollment.payment_plan_id and amounts are changed. Existing enrollment installments stay.

There is no database relationship between these two records

Implemented safe behavior

Rule now applied: when a payment-plan installment is created, updated, deleted, or restored, the schedules of all affected enrollments with no active payment allocation are rebuilt from the current plan templates. An enrollment that already has allocated payments is never changed automatically.

Safe update workflow

1
Load the enrollment and detect whether request.paymentPlanId() differs from the current payment plan ID. If it is the same plan, do not rebuild the schedule.
2
Load all existing enrollment_installment rows with a lock. Check whether any has a payment_allocation (or a paid amount above zero).
3
If payments exist, reject the plan change with HTTP 409 and a clear message. This protects financial history and avoids orphaning payment allocations.
4
If there are no payments, soft-delete or cancel all current enrollment installments. Do this in the same transaction as the enrollment update.
5
Save the new payment plan and amounts on the enrollment, then generate a new set of enrollment installments from the current active templates.
6
Return the enrollment and retrieve its installments again. The API should now return only the new active schedule.

Data integrity rules to keep

RuleReason
Do not delete an enrollment installment physically when it has payment allocations.payment_allocation.enrollment_installment_id depends on it; payment history must remain auditable.
Use soft delete (is_deleted = true) for unpaid old installments.The application already uses soft deletion and its queries filter on deleted = false.
Regenerate only after old rows are made inactive.generateForEnrollment() deliberately prevents duplicate active schedules.
Do not rebuild an enrollment with active payment allocations.Its schedule is financial history. A template change still applies to unpaid enrollments and future enrollments.
The sum of active plan installments cannot exceed payment_plan.total_amount.A fourth 3,000 installment is rejected when the plan total is 9,000. The plan total also cannot be lowered below its current active installment total.

Implemented service methods and endpoint

EnrollmentInstallmentService.synchronizeEnrollmentInstallments(enrollmentId) replaces one unpaid schedule. synchronizeUnpaidEnrollmentsForPaymentPlan(paymentPlanId) is invoked after every plan-installment change. Updating an enrollment to a different plan also synchronizes its schedule.

The frontend can manually request a refresh with POST /api/enrollment-installments/enrollment/{enrollmentId}/synchronize. It returns HTTP 409 if the enrollment has active payment allocations.

This change uses the existing schema; it adds service logic only.
